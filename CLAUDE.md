## О проекте

Сайт записи на тур в Териберку: посетитель заполняет форму на главной и ждёт звонка. Полноценной авторизации нет и не планируется.

Просмотр поступивших заявок на сайте намеренно **не делается** — заявки будут читаться из Telegram-бота (решение от 11.08.2026). Бот живёт **внутри chat-сервиса** ([chat/service/Bot/](src/backend/chat/service/Bot/)) — переехал туда из users 21.08.2026 вместе с чатом (см. «Telegram-бот»): в личке отвечает приветствием с кнопкой-ссылкой на сайт, в группе гидов обслуживает чат. Чтение заявок в него ещё не добавлено, серверная часть готова: `GET /api/admin/application/list` и репозиторий, сортирующий заявки свежими сверху. **Важно**: после переезда бот уже не может читать заявки через репозитории напрямую — ходить придётся в users по HTTP через шлюз с постоянным JWT.

Бренд сайта — «ТериберкаКрай» (en: TeriberkaKray, zh: 捷里别尔卡之境; переименован владельцем 24.08.2026 под домен teriberka-kray.ru, раньше был «Кольский Север»): туры не только в Териберку, а по трём направлениям Мурманской области. ## Команды

```powershell
dotnet build Teriberka.sln                # сборка решения (~20 c, 0 ошибок; ~150 warning'ов — норма)
docker compose up -d postgres             # только БД для локальной разработки
docker compose up --build                 # весь стек: БД + gateway + users + chat + UI + minio + nginx
docker compose up -d minio minio-init     # только хранилище фото (консоль на http://localhost:9001)
```

В контейнерах сайт открывается на **http://localhost** (порт 80 через nginx), а не на :7002 — порт `ui-public` наружу больше не публикуется. Перед первым запуском скопировать `.env.example` в `.env` и заполнить пароли: без `MINIO_ROOT_PASSWORD` и `MEDIA_SECRET_KEY` compose откажется стартовать. Это намеренно — иначе хранилище поднялось бы с дефолтными креденшелами.

Фото для сайта: оригиналы владельца (HEIC/JPG с телефона) лежат в `src/frontend/temp/` (в .gitignore), конвертирует [tools/convert-photos.py](tools/convert-photos.py) — `python tools/convert-photos.py src/frontend/temp src/frontend/temp/webp --width 1600` (нужны `pip install pillow pillow-heif`; `--aspect 5:4` — кроп под слайды полосы «Что вас ждёт», уже готовые файлы пропускает). Готовые кадры заливаются в хранилище (см. «Фото главной»), локальные копии в `wwwroot/img/` остаются фоллбеком.

Локальный запуск сервисов — **обязательно с явным окружением**: `dotnet run` печатает «Using launch settings…», но переменные из `environmentVariables` профиля не применяет, поэтому окружение остаётся Production и `appsettings.Development.json` не читается. Симптомы: у users и chat — `The ConnectionString property has not been initialized`, у шлюза — 500 на любом запросе (`JWT_KEY` = null).

```powershell
dotnet run --project src/backend/users/service/Users.csproj -- --environment Development        # :5012
dotnet run --project src/backend/chat/service/Chat.csproj -- --environment Development          # :5013
dotnet run --project src/backend/gateway/Gateway.csproj -- --environment Development            # :5000
dotnet run --project src/frontend/ui.public.web/UI.Public.Web.csproj -- --environment Development  # :7002
```

Каталог запуска не важен — ContentRoot всегда выставляется в каталог проекта. Альтернатива флагу — задать `ASPNETCORE_ENVIRONMENT=Development` в окружении или передать нужные ключи (`DB_*_CONNECTION_STRING`, `JWT_KEY`, …) переменными среды.

Миграции — у каждого сервиса свой контекст и своя папка `Migrations`; контекст указывать обязательно:

```powershell
dotnet ef migrations add <Name> `
  --project src/backend/users/modules/Users.Infrastructure `
  --startup-project src/backend/users/service `
  --context WriteApplicationDbContext

dotnet ef migrations add <Name> `
  --project src/backend/chat/modules/Chat.Infrastructure `
  --startup-project src/backend/chat/service `
  --context WriteChatDbContext
```

`database update` не нужен: `EnsureDataBaseAsync` в `Program.cs` применяет миграции при старте сервиса (при окружении `Testing` — `EnsureCreated`).

Тестов нет: тестовых проектов не создано, версии тестовых пакетов из `Directory.Packages.props` удалены. При добавлении тестов сначала верните нужные `PackageVersion` — включено central package management, поэтому в `.csproj` версии не указываются.

### Полезное для отладки

- Swagger-агрегатор шлюза: `http://localhost:5000/swagger` (только Development).
- Заявки посмотреть вручную: `GET http://localhost:5000/dev/token` (только Development) отдаёт JWT с ролью `SuperAdmin`, с ним `GET http://localhost:5000/api/admin/application/list` возвращает список. Тем же путём пойдёт Telegram-бот, только с постоянным токеном.
- Чат проверить без сайта: `POST /api/public/chat/send` с телом `{"text":"…"}` возвращает `value` (токен диалога) и `hash` (Ordinal); дальше `GET /api/public/chat/messages?token=<value>&after=0`. Работает и напрямую в chat (`:5013`), и через шлюз (`:5000`).
- Настроить группу гидов: создать приватную группу → добавить бота → в логе chat появится строка «Бота добавили в чат {ChatId}» → этот id в `TG_ADMIN_CHAT_ID` → перезапуск.
- Health: `/health/ready` и `/health/live` у сервисов, `/health` у шлюза и UI.

## Архитектура

### Путь запроса

```
браузер --POST form--> nginx --> UI (Blazor SSR) --Mediator--> ApiCommandHandler --HTTP--> gateway --> users --> Postgres
браузер --чат--------> nginx --> UI (Blazor SSR) --Mediator--> ApiCommandHandler --HTTP--> gateway --> chat  --> Postgres
                                                                                                       chat  --> Telegram (группа гидов)
браузер --фото-------> nginx --> MinIO
```

Наружу смотрит только nginx; всё остальное — во внутренней сети compose. Фото по `/media/*` **не проходят через Kestrel** вообще: они не тратят rate limit сайта и не участвуют в `UseStaticFiles`.

Заявку сайт создаёт через открытый маршрут `/api/public/application/create`. Чтение заявок наружу отдаётся только через `/api/admin/application/list`, закрытый на шлюзе политикой `Admin`. Чат ходит в отдельный сервис через `/api/public/chat/*` (оба маршрута публичные — см. «Чат с посетителем»).

### UI: тема, статика, локализация

- **Почти вся страница — без JavaScript**: тема, язык, формы, карта, карусель и CSS-анимации работают серверно/декларативно. CSP — `script-src 'self'` (inline-скрипты запрещены); главный скрипт — [wwwroot/js/water.js](src/frontend/ui.public.web/wwwroot/js/water.js): самописный WebGL-шейдер воды (~5KB, без библиотек) в полосе `.shore-band`. Он сам выключается при `prefers-reduced-motion`, без WebGL остаётся CSS-фоллбек из трёх слоёв волн, рендер идёт только когда полоса видна (IntersectionObserver). Остальные скрипты того же образца: carousel.js, lightbox.js, restore-scroll.js, theme-toggle.js (тема без перезагрузки, см. «Смена темы/языка»), form-ui.js (см. «Форма без JavaScript»), contact-widget.js (см. «Виджет связи»), parallax.js (см. «Параллакс»), route-progress.js (маршрут дня: линия-прогресс с инерцией поверх пунктира, загорающиеся точки .lit и серый микроавтобус .route-van на кончике линии (инлайн-SVG строится скриптом; вид сверху, капотом по ходу движения — вид сбоку и его поворот на 90° читались «едущим боком»; окна — вырезы fill-rule evenodd, цвет — var(--text-muted); при прокрутке вверх разворачивается капотом вверх — класс .rev, rotate на svg отдельным свойством: transition на transform обёртки тормозил бы позиционирование; фото остановки плавно «наезжает» по мере приближения машинки — скрипт пишет li-переменную --stop-zoom (1..1.07, квадратичная близость в радиусе 340px), CSS применяет scale к img под html.js-route, рамка кадра режет зум overflow-ом); ярус 2 без JS — линию рисует CSS scroll-driven `route-draw`, при reduced-motion — статичный пунктир; позиции маркеров меряются offsetTop, а не getBoundingClientRect — reveal-каскад в момент замера держит карточки в transform) и effects.js (см. «JS-эффекты»). Слои: небо `parallax-sky.svg` с `background-attachment: fixed` (iOS игнорирует) → дальняя гряда `parallax-hills-far.svg` (`::before`; светлее — атмосферная перспектива, с тонкой аврора-подсветкой гребня) → туман `.parallax-mist` (div в разметке; тайл [img/mist.svg](src/frontend/ui.public.web/wwwroot/img/mist.svg) бесшовно дрейфует вбок циклом `translate3d` ровно на ширину тайла; из-за порядка отрисовки — `::after` идёт после детей — туман оказывается между грядами, в долинах) → ближняя гряда `parallax-hills-near.svg` (`::after`; вода и кит-пасхалка) → текст. Силуэты сопок — плавные кривые Безье (треугольные вершины смотрелись примитивно — не возвращать), viewBox 1920×560, нижняя привязка `background-position: center bottom`; светлая тема — те же слои с суффиксом `-light` (25.08.2026 их палитра углублена, а белёсая заливка поверх неба и повышенная непрозрачность тумана убраны: днём сцена читалась пустым местом). Ярусы: (1) база — слои статичны, глубину даёт fixed-небо, работает везде; (2) `@supports (animation-timeline: view())` — слои едут от прокрутки чистым CSS, амплитуда `--parallax-shift` (плюс = отстаёт/дальше, минус = обгоняет/ближе); (3) [js/parallax.js](src/frontend/ui.public.web/wwwroot/js/parallax.js) вешает `html.js-parallax` (CSS-анимации яруса 2 выключаются) и каждый кадр пишет на полосу переменные `--p-*` — инерционный ход (lerp) плюс горизонтальный отклик на мышь на `pointer: fine`; расчёт только пока полоса видна, при `prefers-reduced-motion` скрипт не стартует. Ловушка: запас слоя (отрицательный `inset`) обязан превышать амплитуду хода по обеим осям, иначе на краях оголяется фон.
- **JS-эффекты** — [js/effects.js](src/frontend/ui.public.web/wwwroot/js/effects.js) (вешает `html.js-fx`; при `prefers-reduced-motion` не стартует): (1) инерционная прокрутка — вендоренный Lenis (`js/vendor/lenis.min.js`, `anchors: true`, тач не трогает; рекомендованные стили Lenis — в app.css, секция «js-эффекты»); (2) параллакс-слои `data-speed` по образцу andyhardy.co — элемент отстаёт от прокрутки на долю speed (в hero: `.hero-copy` 0.07, `.hero-map` 0.16), расчёт только около вьюпорта; не совмещать `data-speed` и `.reveal` на одном элементе — оба пишут transform; (3) пружинящие reveal-каскады: селекторам карточек и `.section-head` скрипт ставит `.reveal`/`.appear`, transition-delay по индексу среди соседей (элементы внутри реально прокручиваемого `.carousel-track` — карточки мест на телефоне — каскад не получают: кадр «выезжал снизу» при листании, а все карусели должны вести себя одинаково), CSS-подъём `card-rise` под `html.js-fx` выключен, без JS ничего не прячется; (4) морф-имена для view transitions (ниже).
- **Переходы между страницами** — кросс-документные View Transitions чистым CSS (`@view-transition { navigation: auto }` в app.css): кроссфейд ~0.4 c; Firefox без поддержки просто переходит как обычно, при reduced-motion анимации отключены. Фото места «перелетает» между карточкой главной и страницей места: одинаковый `view-transition-name: place-{slug}` на обоих `<img>` ставит effects.js через CSSOM (инлайновый `style=""` запрещён CSP, `el.style` — нет). Обратный морф (место → главная) может деградировать в кроссфейд: карточки на главной в момент снапшота ещё скрыты reveal-каскадом — это осознанный компромисс.
- **WebGL-«жидкое» фото при наведении** — [js/photo-fx.js](src/frontend/ui.public.web/wwwroot/js/photo-fx.js) (по образцу water.js, без библиотек): один общий канвас `.photo-fx` (fixed, pointer-events: none, z-index 20 — выше карточек, ниже метели и лайтбокса) накладывается поверх фото под курсором (`.place-photo img`, `.detail-photo img`); шейдер даёт рябь от курсора, лёгкий зум и хроматическую аберрацию, сила лерпится 0↔1, при нулевой силе кадр совпадает с исходным фото (cover-маппинг в uv). Только `pointer: fine`, при reduced-motion не стартует, без WebGL остаётся обычный CSS-hover. Ловушка: текстуру НЕ грузить как NPOT без мипмапов — минификация LINEAR даёт зернистый алиасинг; фото пережимается в POT 1024² и включается `LINEAR_MIPMAP_LINEAR` (аспект не важен, uv нормализованы).
- **Карусель отзывов** — тоже без JavaScript: `scroll-snap` (свайп/колесо), на десктопе видны три карточки + край четвёртой как аффорданс листания. Стрелок нет и не будет, пока действует запрет скриптов.
- **Микроанимации** (мерцание звёзд и дрейф авроры в hero) анимируют только `opacity`/`transform` — исполняются GPU-композитором. При добавлении новых анимаций держаться этого правила (не анимировать background/box-shadow/filter) и не забывать ветку `prefers-reduced-motion`.
- **Метель** (`.blizzard` в MainLayout) — fixed-слой поверх всего сайта: порыв ~14 с раз в ~40 с. «Таймер» — длинный keyframes-цикл opacity на контейнере; движение снега — бесшовный диагональный `translate3d` слоёв ::before/::after ровно на размер тайла паттерна (слои больше вьюпорта на тот же тайл, чтобы края не оголялись). Цвет снега — `--snow-rgb` (в светлой теме серо-голубой). При `prefers-reduced-motion` слой скрыт целиком.
- Скриншоты для проверки вёрстки: headless Chrome на Windows не отдаёт окно уже ~500px, поэтому мобильную ширину снимать через CDP `Emulation.setDeviceMetricsOverride` (+`Page.captureScreenshot` с `captureBeyondViewport`), а не `--window-size`. На таких скриншотах fixed-фоны параллакс-полос выглядят пустыми — это артефакт съёмки, вживую фон на месте. Вторая ловушка съёмки: при `captureBeyondViewport` карточки под reveal-каскадом effects.js остаются с opacity 0 (IntersectionObserver за вьюпортом не срабатывает) — блок выглядит пустым; лечится эмуляцией `prefers-reduced-motion: reduce` через CDP (effects.js тогда не стартует) либо окном в полную высоту страницы.

### Форма без JavaScript

Фронтенд работает на **static SSR** — интерактивный render mode не зарегистрирован и `blazor.web.js` не подключён, поэтому `@onclick`/`@onsubmit` в браузере не выполняются. Форма серверная: `EditForm` + `[SupplyParameterFromForm]` + `FormName`, обработка на POST, после успеха — редирект на `/?sent=true` (post-redirect-get), чтобы F5 не отправлял заявку повторно. Форма одна — компонент [ApplicationForm.razor](src/frontend/ui.public.web/Components/ApplicationForm.razor); ветка `Custom` (`/?tour=custom#apply`) меняет кикер/заголовок/подводку и предвыбирает маршрут `custom`, а POST, FormName и обработка общие — отдельных форм не плодить. Ссылок на эту ветку со страницы больше нет (блок «Индивидуальный тур» убран 25.08.2026), но сама она рабочая. Кикер, заголовок и подводка живут **не в карточке, а в шапке секции** (`.section-head.apply-head` в Home.razor, 25.08.2026: у формы должен быть такой же белый заголовок над карточкой, как у остальных блоков); после отправки шапка не рендерится — там уже карточка «спасибо» со своим заголовком. Список «что будет после заявки» — четыре пункта `FormPoint1..4` в две колонки от 700px (три оставляли дыру справа, владелец 25.08.2026). Поля — `Title` (имя, необязательно), `Phone` (обязателен) и `Route` (маршрут, по умолчанию Териберка; миграция `AddApplicationRoute`, 21.08.2026): поля даты, числа людей и пожеланий убраны из контракта, сущности и БД (миграция `RemoveApplicationDetails`, 21.08.2026) — не возвращать без решения владельца. Маршрут хранится **кодом** (`teriberka` / `lovozero` / `tersky` / `custom`, константы в [ApplicationRoutes](src/contracts/Applications.Contracts/ApplicationRoutes.cs)), а названия берутся из resx — `MapSpot1..3` и `RouteCustomTitle`; переименование маршрута не требует миграции; валидатор принимает только известные коды, иначе подделанный POST записал бы в заявку произвольную строку. **Новый код маршрута — это правка контрактов, общих с бэком**: тот же валидатор работает в users через `ValidatorBehavior`, поэтому без пересборки контейнера (`docker compose up -d --build --force-recreate api-users`) сайт покажет «Выберите маршрут из списка» на новый вариант. `--build` без `--force-recreate` образ пересобирает, а контейнер оставляет старый — проверено 25.08.2026. Выбор маршрута — **карточки-радиокнопки, а не `<select>`** (владелец, 25.08.2026): у каждого варианта видно описание (`Dir{i}Text`, у индивидуального — `RouteCustomText`), а подменять текст под выбранный пункт без JavaScript нельзя, поэтому все описания показаны сразу. Инпуты обычные (`<input type="radio">`), не `InputRadio`; **имя поля обязано нести префикс модели — `Model.Route`** (так же называет поля `InputText`), иначе выбор молча не доезжает до сервера, а валидатор ругается на пустой маршрут. Подсветка выбранной карточки — `input:checked + .route-option-box`, без `:has()`. Ветка `Custom` (`/?tour=custom#apply`) заодно предвыбирает маршрут `custom`. Фото-шапки у карточки формы больше нет (владелец, 25.08.2026) — вместе с ней удалены `.apply-photos`; кнопка отправки со своей сноской собрана в колонку `.form-submit-main`, симметричную кнопке бота, а сам ряд на десктопе центрируется (`justify-content: center`) — прижатый влево он оставлял дыру справа. Карточка формы шире прежнего (900px против 720): узкая колонка под трёхколоночной лентой мест смотрелась случайной, но во всю ширину контейнера (1080) её не растягиваем — подводка ушла бы за сотню символов в строке, поэтому у `.apply-lead` ещё и `max-width: 62ch`. **Якорь `#apply` висит на самой форме** (и на карточке «спасибо»), а не на секции: ссылки «Записаться» должны приводить к первому полю, а не к шапке карточки; `scroll-margin-top` — на `.apply-form`/`.sent-card`. Antiforgery-токен `EditForm` добавляет сам, `app.UseAntiforgery()` включён. Валидация: [js/form-ui.js](src/frontend/ui.public.web/wwwroot/js/form-ui.js) ставит форме `novalidate`, ведёт **маску телефона** (в поле остаются только цифры, разметку «+7 900 000-00-00» скрипт расставляет сам; «8…» и «9…» приводятся к +7, номер с явным «+» и другим кодом остаётся международным без разметки; курсор возвращается к той же цифре — маска отдаёт флаг `added`, когда код страны дописан ею, иначе курсор вставал после «7» и первая цифра уезжала в конец), проверяет телефон (та же regex, что в валидаторе, **плюс длина**: 11 цифр у российского, ≥8 у зарубежного — иначе «+7 900» проходило бы серверную regex обрывком) и согласие и показывает подсказки `.field-hint-error` под полями (тексты — `data-val-*` на форме из resx); без JS — HTML5-атрибуты и системные пузыри; на сервере — FluentValidation-валидатор из контрактов (в UI внедряется как `IEnumerable<IValidator<T>>`, ошибки рендерятся теми же классами), плюс тот же валидатор отрабатывает в сервисе через `ValidatorBehavior`. Стили ошибок — мягкая подсветка поля в `--danger` + подсказка с маркером «!»; чекбокс согласия — свой (`appearance: none`, галочка из `::after`, аврора-фон при `:checked`), нативный в тёмной теме выглядел инородно.

При переходе на интерактивный рендеринг (`AddInteractiveServerComponents` / `AddInteractiveServerRenderMode`) форму придётся переписать под обычные обработчики событий.

### Контракты общие для бэка и фронта

`src/contracts/*` ссылаются и сервисы, и Blazor-проект. Один и тот же тип (`ApplicationCreateCommand`) — это одновременно Mediator-запрос в UI, Mediator-запрос в сервисе и тело `[FromBody]` у HTTP-эндпоинта. Базовые типы в [src/contracts/Contracts/](src/contracts/Contracts/): `Command`, `DeleteCommand`, `Query<TDto>`, `ListQuery<TDto>`, `PagedListQuery<TDto,TQuery>`, `Dto`, `AuditableDto` и базовые валидаторы.

Следствие: **чтобы UI мог вызвать эндпоинт, в `ui.public.web/Handlers` нужен свой `ApiHandler`-наследник**, иначе Mediator не найдёт обработчик (генератор предупреждает `MSG0005`, а `Send` падает в рантайме).

### Обобщённый CQRS-конвейер: код фичи — почти только типовая обвязка

Всё реализовано в generic-виде в `src/backend/shared`, поэтому фича обычно = набор пустых наследников:

- Handler'ы: `CreateCommandHandler<>`, `UpdateCommandHandler<>`, `DeleteCommandHandler<>`, `SingleQueryHandler<>`, `ListQueryHandler<>`, `PagedListQueryHandler<>`.
- Репозитории `CommandRepository<,>`, `SingleQueryRepository<,,>`, `ListQueryRepository<,,>` зарегистрированы как open generic в `AddApiServices`. Свой репозиторий нужен только для нестандартной выборки — тогда наследуешься и переопределяешь `BuildDbQuery` / `ProcessDbQuery` / `ProcessTextQuery` / `ProcessSorting` / `ProjectSimple`; Scrutor подхватит наследника автоматически и он победит open-generic регистрацию (пример: [ApplicationListQueryRepository](src/backend/users/modules/Users.Infrastructure/DataAccess/Repositories/Application/ApplicationListQueryRepository.cs) сортирует заявки свежими сверху).
- Маппинг: Mapperly, регистрация по соглашению об имени — класс должен называться `*DtoMapper` / `*EntityMapper` / `*RpcMapper` и лежать в сборке, имя которой заканчивается на `Infrastructure.dll` (`ConfigureMappers`). Переименуешь — маппер молча не зарегистрируется.
- Валидация: `ValidatorBehavior<,>` подключается в `Configurator.ConfigureDependencies`, валидаторы находятся по сборкам автоматически.

Сквозной референс — сущность `Application` (заявка): [contracts](src/contracts/Applications.Contracts/), [entity](src/backend/users/modules/Users.Domain/Entities/Application.cs), [EF config](src/backend/users/modules/Users.Infrastructure/DataAccess/Config/ApplicationConfig.cs), [mappers](src/backend/users/modules/Users.Infrastructure/DataAccess/Mappers/ApplicationMapper.cs), [handlers](src/backend/users/modules/Users.Application/Handlers/Application/), [эндпоинты](src/backend/users/service/Configurator.cs), [UI handler](src/frontend/ui.public.web/Handlers/ApplicationHandlers.cs), [страница с формой](src/frontend/ui.public.web/Features/Home/Pages/Home.razor).

Чек-лист новой сущности: контракт → entity → EF config → мапперы → handler'ы → эндпоинт в `ConfigureEndPoints` → **маршрут в шлюзе** (если нужен внешний доступ; новому сервису нужен ещё и **кластер**) → миграция → handler + страница в UI. Забытый маршрут в шлюзе — самая частая причина «эндпоинт есть, но недоступен».

Нестандартный случай — чат ([Chat.Contracts](src/contracts/Chat.Contracts/), chat-сервис): там сообщение нельзя создать одним маппингом из команды, поэтому вместо generic `CommandRepository` написан свой [ChatRepository](src/backend/chat/modules/Chat.Infrastructure/DataAccess/Repositories/ChatRepository.cs). Он не наследует ни один из базовых репозиториев, а значит **Scrutor его не найдёт** — регистрируется руками в `Configurator`.

### URL-конвенция и авторизация

Формат `/api/{role}/{group}/{action}`, где `role` ∈ `public` | `private` | `admin` (`Api.Constants.UrlRestrictions`). Эндпоинты объявляются fluent-билдером:

```csharp
app.MediateGroup("application", Constants.UrlRestrictions.Admin)
   .List<ApplicationListQuery, ApplicationDto>();              // GET /api/admin/application/list
app.MediatePostCommand<ApplicationCreateCommand>("application", "create");  // POST /api/public/application/create
```

Действия билдера: `Single` → `get`, `List` → `list`, `PagedList` → `pagedList`, `Create` → POST `create`, `Update` → PUT `update`, `Delete` → DELETE `delete/{id}`.

**Роль в URL — только сегмент пути, сервис её не проверяет.** Аутентификация и авторизация целиком на шлюзе: JWT bearer + политика `Admin` (claim role = 1/2, см. `UserRole`), назначаемая маршруту через `AuthorizationPolicy` в [gateway/appsettings.json](src/backend/gateway/appsettings.json). Отсюда требование к развёртыванию: **users-сервис не должен быть доступен из внешней сети** — сам он никого не проверяет и доверяет вызывающему. В `docker-compose.yml` его порт 5012 опубликован только для локальной отладки.

### Виджет связи

Плавающая круглая кнопка в правом нижнем углу ([ContactWidget.razor](src/frontend/ui.public.web/Components/ContactWidget.razor), подключается в `MainLayout`): фото гида в аврора-кольце, по клику вверх разворачивается «ёлочка» каналов — звонок (`CONTACT_PHONE`), Telegram-бот (`TG_BOT_URL`), MAX (`MAX_URL`) и чат на сайте (всегда, см. «Чат с посетителем»). Пузырь `.contact-teaser` («Остались вопросы?») объясняет, что фото — это путь к диалогу: одно лицо так не читается.

- **Меню — нативный `<details>` без JavaScript**, как `.nav-burger` и маркеры карты: закрытие кликом вне — фиксированный оверлей в `.contact-fab::before`. Отсюда та же ловушка: на `.contact-widget` и `.contact-fab` **нельзя** вешать `transform`/`filter`/`backdrop-filter` — они создают containing block и ломают оверлей. Панель обязана иметь `z-index: 1` (оверлей — `0`), иначе пункты видно, но нажать нельзя.
- **Раскрытие анимируется `animation`, а не `transition`**: `details` показывает содержимое скачком из `display: none`, переходу не от чего стартовать. Задержки «ёлочки» считаются `:nth-last-child` — новый канал дописывается в список без правки CSS.
- **Угол принадлежит виджету**: `.scrollers` и панель чата подняты над ним через токен `--fab-size` (`bottom: calc(16px + var(--fab-size) + 12px)`). Сам размер кнопки — 56px, на десктопе (≥900px) 72px: в углу она единственный «живой» элемент, и мелкий кругляш там терялся (владелец, 25.08.2026). Меняешь размер — правишь только токен, соседи подвинутся сами. Липкая полоса заявки внизу (`.mobile-apply` + `sticky-cta.js`) **удалена 21.08.2026** — два фиксированных элемента внизу мешали друг другу; её роль на узких экранах играет кнопка `.header-apply` в шапке.
- Каналов нет — виджета нет вовсе; ровно один — кнопка ведёт прямо в него, без меню.
- Иконка MAX — нейтральный глиф, а не фирменный знак: логотип это торговая марка, а CDN запрещён CSP. Появится официальный SVG — класть в `wwwroot/img/`.
- [contact-widget.js](src/frontend/ui.public.web/wwwroot/js/contact-widget.js) добавляет только то, чего `<details>` не умеет: Esc и сворачивание после выбора канала. Без него виджет полностью рабочий.
- Следующий шаг — пункт «Чат на сайте» (ключ `ContactChat` уже заведён в трёх resx): серверная часть чата готова, не хватает UI (см. ниже).

### Чат с посетителем

Плавающий чат на сайте: посетитель пишет вопрос → сообщение в БД chat-сервиса → пуш в приватную Telegram-группу гидов → гид отвечает **reply** прямо в группе → ответ появляется в чате на сайте. Сделан **отдельным сервисом** 21.08.2026: чат тянет за собой Telegram long polling, а он привязывает сервис к одному инстансу — держать на этом ещё и users было бы неоправданно.

Работает целиком: серверная часть (сервис `chat`, бот) плюс UI — панель [ChatPanel.razor](src/frontend/ui.public.web/Components/ChatPanel.razor), эндпоинты `/chat/send` и `/chat/poll` в UI и [chat.js](src/frontend/ui.public.web/wwwroot/js/chat.js).

- **UI чата** ([ChatPanel.razor](src/frontend/ui.public.web/Components/ChatPanel.razor)): панель открывается пунктом виджета связи. Без JavaScript пункт — обычная ссылка `?chat=open`: панель и историю рендерит сервер, отправка идёт POST'ом на `/chat/send` и возвращается сюда же (PRG). С JavaScript [chat.js](src/frontend/ui.public.web/wwwroot/js/chat.js) открывает её на месте и опрашивает `/chat/poll` — 3 с при открытой вкладке, 15 с в фоне, экспоненциальный откат до минуты при ошибках. Историю сервер тянет **только при `?chat=open`**, иначе каждый рендер каждой страницы ходил бы в chat-сервис.
- **Эндпоинты живут на сайте, а не на шлюзе** (`Program.cs`, до `MapRazorComponents`): в chat ходит сервер UI, он же владеет cookie. `POST /chat/send` сам проверяет antiforgery (`UseAntiforgery` покрывает только form-binding, а форму читаем вручную) и отвечает JSON при `Accept: application/json`, иначе редиректом — один код-путь и для JS, и без него. `GET /chat/poll` отдаёт `no-store` и `Vary: Cookie`.
- **Cookie `chat_sid`** ([ChatCookie](src/frontend/ui.public.web/Features/Chat/ChatCookie.cs)) — HttpOnly, Lax, 90 дней (совпадает с `CHAT_RETENTION_DAYS`). Значение приходит из сервиса в `ExecuteRequestResult.Value` и ставится в эндпоинте: из Razor-компонента cookie не поставить, как и у `/set-culture`.
- **Онлайн-статус** — [ChatSchedule](src/frontend/ui.public.web/Features/Chat/ChatSchedule.cs) по ключам `CHAT_HOURS` и `CHAT_TZ`: в часы работы «отвечаем за несколько минут», вне — «ответим утром». Кривой формат не прячет виджет, а пишет warning и считает, что чат отвечает всегда.
- **Лимитер UI** получил свои партиции для `/chat/poll` (40/мин) и `/chat/send` (10/мин): иначе поллинг съедал бы общий лимит страницы, а отправка — квоту формы заявки (5 за 5 минут).
- Тексты для скрипта едут `data-*` атрибутами (inline-скрипт запрещён CSP), сообщения рисуются только через `textContent` — `HtmlSanitizer` в проекте ни к чему не подключён, а текст приходит из чужой реплики.
- **Сущности** ([Chat.Domain/Entities/Chat.cs](src/backend/chat/modules/Chat.Domain/Entities/Chat.cs)): `ChatSessionEntity` (диалог) и `ChatMessageEntity`. Связь — плоским `SessionId`, без навигационных свойств и `Include`.
- **Идентификация диалога — только секретный `Token`** (32 байта CSPRNG в base64url), он же значение cookie `chat_sid` на сайте. Именно отдельный токен, а не `Id`: `Id` генерируется последовательным Guid'ом и предсказуем по соседям. Контакты, IP и User-Agent посетителя не хранятся сознательно.
- **Курсор поллинга — `Ordinal`** (1..N внутри диалога), не время: `Audit.CreatedAt` приходит из `NOW()`, и две вставки в одну микросекунду заставили бы фильтр «строго больше» пропустить сообщение. Защищён уникальным индексом `(SessionId, Ordinal)`.
- **Эндпоинты**: `POST /api/public/chat/send` (пустой или неизвестный токен заводит новый диалог — иначе первое сообщение отправить нельзя; в ответе `value` = токен сессии, `hash` = `Ordinal`) и `GET /api/public/chat/messages?token=…&after=N`. Без токена выборка пустая — чужую переписку получить нельзя. `ChatAdminReplyCommand` эндпоинта не имеет: её шлёт только бот изнутри процесса.
- **Антиспам в самом сервисе** (кроме лимитеров сайта и шлюза): ≤1000 символов, ≤20 сообщений на диалог за 10 минут и ≤100 всего → `ExcecuteCommandException(TooManyRequests)` → 429. Лимиты — в [ChatLimits](src/contracts/Chat.Contracts/ChatLimits.cs), общем для бэка и фронта.
- **Доставка в Telegram — через outbox, а не напрямую из обработчика**: `AfterCommit` кладёт id в `IChatNotificationQueue` (Channel в памяти), [ChatNotificationDispatcher](src/backend/chat/service/Bot/ChatNotificationDispatcher.cs) отправляет и проставляет `TgMessageId`. Держать POST посетителя на сетевом вызове Telegram нельзя, а падение мессенджера не должно ломать отправку. Очередь не переживает рестарт — **это нормально**: недоставленное видно в БД (`TgMessageId IS NULL AND Direction = 0`, под это есть частичный индекс), диспетчер раз в минуту подметает такие сообщения моложе 24 часов.
- **Reply → диалог**: сначала по `ChatMessages.TgMessageId`, потом по `ChatSessions.TopicMessageId` («шапка» диалога в группе). Уникальный индекс по `TgMessageId` плюс проверка в handler'е отсекают дубль при повторной доставке апдейта.
- Текст посетителя уходит в группу с `ParseMode.Html`, поэтому **обязательно экранируется** (`WebUtility.HtmlEncode`), иначе Telegram отвергнет сообщение или съест кусок текста.
- **Тексты сообщений не логируются нигде** — только `SessionId`, `Ordinal` и статус. `EnableSensitiveDataLogging` не включать.
- **Чистка по сроку хранения** ([ChatRetentionService](src/backend/chat/service/ChatRetentionService.cs), `CHAT_RETENTION_DAYS`, по умолчанию 90 дней) — **жёсткое** `ExecuteDelete`, вопреки общему для проекта мягкому удалению: в чате лежат ПД, `IsDeleted = true` оставил бы их в базе навсегда. Копию в Telegram это не убирает — Bot API не даёт удалять сообщения старше 48 часов, о чём должна честно говорить политика конфиденциальности.

### Telegram-бот

Хостится как `BackgroundService` в **chat-сервисе** ([chat/service/Bot/](src/backend/chat/service/Bot/), регистрация в `Configurator.ConfigureDependencies`), отдельного деплоймента нет. Long polling — исходящее соединение, поэтому закрытость сервиса от внешней сети боту не мешает.

**⚠️ chat-сервис нельзя масштабировать горизонтально**: long polling обязан работать ровно в одном экземпляре — два процесса с одним токеном начнут отбирать апдейты друг у друга, и ответы гидов будут теряться. Раньше от этого зависело только приветствие бота в users, теперь — вся входящая половина чата. Понадобится масштабирование — бота выносить в отдельный процесс.

- Клиент Telegram создаётся один на процесс в [TelegramBotAccessor](src/backend/chat/service/Bot/TelegramBotAccessor.cs); им пользуются и polling, и доставка сообщений.
- Без `TG_BOT_TOKEN` (или при отвергнутом Telegram'ом токене) бот пишет в лог и выключается, не мешая API. Без `TG_ADMIN_CHAT_ID` чат работает и сохраняет переписку, но в группу ничего не уходит — недоставленное уедет само, как только ключ появится.
- **`DropPendingUpdates = false`** (раньше было `true`): тем же каналом приходят ответы гидов, терять их нельзя. От пачки приветствий на вчерашние `/start` защищает фильтр по возрасту сообщения (10 минут). Telegram хранит недоставленные апдейты только 24 часа — за этим пределом ответ теряется независимо от нас.
- `AllowedUpdates = [Message, MyChatMember]`. `MyChatMember` нужен для настройки: добавили бота в группу — её id сразу виден в логе, его и класть в `TG_ADMIN_CHAT_ID`.
- **Privacy mode выключать не нужно**: в группе бот по умолчанию видит команды и reply на собственные сообщения — наш сценарий ровно такой. Обратная сторона: свободное (не reply) сообщение гида бот не увидит вовсе и подсказку на него не отправит.
- Язык ответа в личке — по `Message.From.LanguageCode`: `ru` → русский, `zh*` → китайский, остальное и пустой тег → английский. Язык служебных сообщений **в группе** — из `TG_ADMIN_LANG` (группа одноязычная). Тексты — switch в [BotTexts.cs](src/backend/chat/service/Bot/BotTexts.cs), UI-локализация (resx) тут не используется.
- Ссылка на бота в шапке сайта рендерится только при заданном `TG_BOT_URL` (в Development стоит плейсхолдер `https://t.me/kola_north_bot` — заменить на реальный username бота).

### Фото главной: хранилище и reverse proxy

Кадры полосы «Что вас ждёт» лежат **не в репозитории, а в хранилище** — владелец заливает их через веб-консоль MinIO, без коммита и пересборки сайта. Ради этого S3 и заведён; остальная статика (css, js, SVG-слои, `og.jpg`) остаётся в `wwwroot` и версионируется вместе с кодом — иначе появилось бы состояние «новая разметка + старый CSS».

- **Раскладка бакета** — один префикс `hero/`, имена файлов ровно те же, что в [HeroSlides](src/frontend/ui.public.web/Features/Home/HeroSlides.cs) (`hero-edge.webp` и т.д.). Имя обязано быть в нижнем регистре из `a-z0-9-` и заканчиваться на `.webp`: кириллица, пробелы и верхний регистр дают percent-encoding и «файл залит, а на сайте его нет». Непринятые файлы [MediaCatalog](src/frontend/ui.public.web/Features/Media/MediaCatalog.cs) пишет в лог поимённо — искать причину молча не придётся.
- **Как заливать**: `ssh -L 9001:127.0.0.1:9001 user@server` → `http://localhost:9001` → бакет `media` → папка `hero` → Upload. Консоль наружу не публикуется никогда, только через туннель.
- **`MediaCatalog`** держит снимок содержимого бакета в памяти, обновляет его `MediaRefresher` раз в `MEDIA_REFRESH_MINUTES` (он же — задержка «залил → видно на сайте»). Ходить в хранилище на рендере нельзя: главная отрисовывается на каждый запрос. Хранилище недоступно — живёт прошлый снимок, страница не падает.
- **Порядок источников в Home.razor**: объект в хранилище → одноимённый файл в `wwwroot/img` (так работает локальный `dotnet run` без докера) → `placeholder.svg`. Локальные копии кадров сознательно оставлены как фоллбек.
- **Версия в URL** (`?v=<время изменения объекта>`) проставляется автоматически: картинки кэшируются на 30 суток, и без неё перезалитое под тем же именем фото посетитель увидел бы только через месяц. nginx проксирует в MinIO **только путь**, поэтому лишний параметр до хранилища не доходит. Правило «новое фото — новое имя» из-за этого не нужно.
- **Пустой `MEDIA_ENDPOINT` выключает хранилище целиком** — сайт работает на локальных файлах. Та же идиома, что у `TG_BOT_URL` и `MAX_URL`.
- **Единственная копия фото — том `minio_volume`.** Он уже терялся при перестроении compose; оригиналы держать у себя локально, плюс регулярный `mc mirror --overwrite local/media <куда-то>`.

**nginx — единственная точка входа** ([infra/nginx/templates/default.conf.template](infra/nginx/templates/default.conf.template)): `/media/*` уходит в MinIO, всё остальное — в `ui-public`. Отсюда главное свойство: фото отдаются **с того же домена**, поэтому CSP (`img-src 'self' data:`) трогать не нужно и второй сертификат не нужен. Грабли, каждая из которых уже была наступлена:

- **`proxy_set_header X-Forwarded-*` обязателен.** nginx, в отличие от Caddy, не ставит эти заголовки сам, а `USE_FORWARDED_HEADERS` у UI включён. Забудешь — Kestrel увидит адрес контейнера nginx, один на всех, и rate limiter станет общим счётчиком: шестая заявка за 5 минут словит 429 у всех подряд.
- **Конфиг — шаблон, его прогоняет envsubst** (штатный механизм образа). `NGINX_ENVSUBST_FILTER: "^(SITE_|MEDIA_)"` в compose **обязателен**: без фильтра envsubst подставит пустые значения в переменные самого nginx (`$uri`, `$binary_remote_addr`, `$proxy_add_x_forwarded_for`), и конфиг молча станет нерабочим.
- **`resolver 127.0.0.11` обязателен**, потому что в `proxy_pass` медиа есть переменная `$obj`: из-за неё nginx резолвит имя upstream'а на каждом запросе, а не на старте, и без резолвера отвечает 502 «no resolver defined to resolve minio».
- **Защита маршрута — сама регулярка** `~* ^/media/(?<obj>.+\.webp)$`: перечисление бакета (`?list-type=2`), `.svg`, `.html` и подписанные ссылки в этот `location` просто не попадают и получают 404. Плюс `limit_except GET HEAD`. Порт 9000 (S3 API) не публикуется вовсе.
- **`?` в конце `proxy_pass`** отбрасывает query — до MinIO она не доходит.
- **`Content-Type` переопределяется только парой `proxy_hide_header` + `add_header`**: `add_header` сам по себе не заменяет заголовок, а MinIO при заливке некоторыми клиентами ставит `application/octet-stream`, и браузер тогда предлагает скачать файл вместо показа. По той же причине прячется чужой `X-Content-Type-Options` — иначе он придёт дважды.
- **`add_header` без `always`** не попадает в ответы 4xx/5xx; **`add_header` внутри `location` отменяет унаследованные** из `server` — перечислять все нужные в каждом блоке.
- **`Cache-Control` 30 суток, но без `immutable`**: версия в query и так решает вопрос, а `immutable` спрятал бы правку даже по Ctrl+F5.
- **`server_tokens off`** убирает версию, но полностью снять заголовок `Server` стоковый nginx не умеет (нужен модуль `headers_more`, которого в официальном образе нет) — снаружи видно `Server: nginx`.
- **`limit_req` на `/media`** (30 r/s, burst 60): маршрут публичный, фото весят сотни килобайт, без лимита их можно выкачивать в цикле. Это и было причиной выбрать nginx вместо Caddy.
- **TLS ещё не включён.** В конфиге лежит готовый закомментированный блок `server { listen 443 ssl; }` и работающий `location /.well-known/acme-challenge/`. Порядок: A-запись на сервер → `SITE_DOMAIN` = домен → `certbot certonly --webroot -w /var/www/certbot -d домен` (первый заход с `--staging`: у Let's Encrypt лимит 5 неудач в час) → раскомментировать 443-блок → добавить редирект и сервис продления. **HSTS вписывать только в 443-блок**: на `http://localhost` он заставил бы браузер запомнить localhost как https-only и сломал бы прочие локальные проекты. Том `letsencrypt` терять нельзя.

### Данные

Сущности разложены по сервисам. В users — `Application` (заявки, то, ради чего сайт) и `User` (эндпоинты `/api/admin/user/*` есть, но потребителей у них пока нет). В chat — `ChatSession` и `ChatMessage` (см. «Чат с посетителем»).

- Раздельные контексты чтения и записи в каждом сервисе: `ReadApplicationDbContext`/`WriteApplicationDbContext` в users и `ReadChatDbContext`/`WriteChatDbContext` в chat (read-контексты глобально NoTracking), строки подключения `DB_READ_CONNECTION_STRING` / `DB_WRITE_CONNECTION_STRING` у каждого свои.
- Схема выбирается через `search path` в строке подключения (users → `search path=users,public`, chat → `search path=chat,public`) — одна база, разные схемы; переезд на отдельные БД делается правкой строки подключения, без изменений в коде. EF генерирует SQL без указания схемы. `WriteDbContext.MigrateAsync` перед миграцией создаёт схему, расширения `citext` / `pg_trgm` / `btree_gin` и коллацию `case_insensitive` — поэтому новую схему заводить руками не нужно, достаточно строки подключения.
- Базовые контексты зарегистрированы factory-алиасами на конкретные (`AddScoped<ReadDbContext>(sp => sp.GetRequiredService<TR>())`), иначе `UnitOfWork` и репозиторий получили бы разные инстансы. Подробности — в комментарии внутри `AddPersistence`.
- Оптимистичная блокировка: `Entity.Xmin` замаплен на системный столбец `xmin` как concurrency token; update-команды несут `Xmin`, репозиторий кладёт его в `OriginalValue`.
- Удаление мягкое: `IsDeleted = true`, list-запросы фильтруют по нему (`GetBaseDbQuery`). Исключение — чистка переписки чата по сроку хранения: там жёсткое `ExecuteDelete`, потому что мягкое оставило бы персональные данные в базе навсегда.
- `SaveChanges` в handler'ах не вызывается: `CommandHandler.Handle` делает `UnitOfWork.CommitAsync` после `ExecuteCommand`; для пост-коммит эффектов — `AfterCommit`.
- `EntityConfig` по умолчанию навешивает **уникальный** индекс на `Title` — где заголовки повторяются, переопределяй `ConfigureIndexes` (так сделано в `ApplicationConfig`: два тёзки должны иметь возможность записаться). `UserEntity.Title` — stored computed column из `FirstName`/`LastName`.

### Безопасность

Что уже настроено и почему именно так:

- **Rate limiting в двух местах.** Форма отправляется POST'ом на сам сайт, а API-вызов делает сервер UI, поэтому ограничение только на шлюзе обходится отправкой формы в цикле. В UI глобальный лимитер делит запросы по методу: POST — 5 за 5 минут на IP, остальное — 300 в минуту. На шлюзе маршрут `applications-public` помечен политикой `public-form` (те же 5 за 5 минут), `chat-public` — политикой `public-chat` (300/мин), плюс глобальные 300/мин; `/health` из лимитов исключён. Счётчики живут в памяти процесса — при нескольких инстансах фактический лимит умножается на их число.
- **Лимиты шлюза для чата — не «на посетителя».** Шлюз видит IP сервера UI (страницы рендерит он, а не браузер), поэтому `public-chat` — общий потолок пропускной способности чата. Справедливость между посетителями обеспечивает только лимитер сайта, и когда на UI появятся эндпоинты чата, ему понадобятся отдельные партиции по пути (глобальный лимитер UI — именно `GlobalLimiter`, `.RequireRateLimiting(...)` его не заменит, а `.DisableRateLimiting()` снимет вообще всё).
- **CORS сознательно узкий и, по сути, задел на будущее.** Браузер в API не обращается (страницы рендерит сервер UI), поэтому политика собирается строго из `UI_APP_URL`, без `AllowCredentials`, и не регистрируется вовсе, если список пуст. Прежняя dev-ветка с `SetIsOriginAllowed(_ => true)` + `AllowCredentials()` убрана: такое сочетание разрешало любому сайту читать ответы API с cookie пользователя.
- **Заголовки ответа UI**: CSP (`script-src 'self'` — только собственные файлы скриптов, inline-скрипты запрещены; `style-src 'self'` — никаких inline-стилей), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `Permissions-Policy`. Заголовок `Server` отключён у обоих сервисов. Для сторонних скриптов (капча, метрика) их домены добавляются в `script-src` точечно.
- **Antiforgery** — включён (`UseAntiforgery`), токен в форму добавляет `EditForm`.
- **Валидация телефона** по формату, а не только по длине: поле уходит оператору и в бота, без формата форма становится каналом для спам-ссылок. Имя необязательно и ограничено длиной.
- **Лимит тела запроса** в UI — 64 КБ (загрузок файлов нет). Появится загрузка — поднять.
- **`USE_FORWARDED_HEADERS`** у UI в compose включён (`true`) — сайт стоит за nginx. Флаг и отсутствие публичного порта у `ui-public` **связаны намертво**: код делает `KnownProxies.Clear()`, то есть доверяет `X-Forwarded-For` от кого угодно, и стоит открыть порт наружу — любой обойдёт rate limiting одним заголовком. Без флага было бы не лучше: Kestrel видел бы адрес контейнера nginx, один на всех, и шестая заявка за 5 минут ловила бы 429 у всех подряд. Проверяется так: исчерпать лимит `/chat/poll` (40/мин) с одного адреса и тут же сходить с другого — второй должен получить 200.
- **users и chat не должны торчать в интернет** — они никого не проверяют и доверяют вызывающему; в `docker-compose.yml` их порты (5012 и 5013) открыты только для локальной отладки.

Согласие на обработку ПД и политика конфиденциальности **есть, но как заглушки** (добавлены 18.08.2026): чекбокс `.consent` в форме проверяется только в браузере (`required` + form-ui.js), в контракт не входит и сервером не валидируется; страница `/privacy` — честный черновик с фейковыми реквизитами (см. «Контент-плейсхолдеры»). Перед запуском: настоящий текст политики и реквизиты, при желании — серверная проверка согласия (поле в контракте + валидатор).

Чего ещё нет и о чём стоит помнить: капчи или honeypot (rate limiting не спасает от распределённого спама), бэкапов БД и хранилища фото, TLS-сертификата (реверс-прокси уже есть — nginx; включение TLS описано в разделе про него). `EnableSensitiveDataLogging` в EF не включён — включать нельзя, иначе телефоны попадут в логи.

### Остатки, которые ещё ни к чему не подключены

- В `UI.Shared` из handler'ов используется только `ApiCommandHandler`; `ApiSingleQueryHandler`, `ApiListQueryHandler`, `ApiPagedListQueryHandler`, `QueryBuilder`, `ConfigService` и `AuthorizationHeaderHandler` (с ключом `API_TOKEN`) остались от страницы заявок и сейчас без потребителей.
- `SanitizationBehavior` + `HtmlSanitizer` написаны, но ни один сервис не добавляет behavior в `PipelineBehaviors`.
- Серверная локализация (`SharedStrings.resx` в Api, `UsersStrings.resx` в users, `SharedLocalizer`) заведена, но не используется — рабочая локализация есть только в UI (`SharedResource`).
- Абстракции `ISlugable` / `IPictureable` и поле `Dto.ImagePath` есть в базовых типах, но ни одна сущность их не реализует; файлового сервиса и хранилища в проекте нет.

## Конфигурация

Настройки — плоские ключи в стиле переменных окружения (не иерархические секции), читаются напрямую из `IConfiguration`:

| Сервис | Ключи |
|---|---|
| UI | `API_URL`, `API_TOKEN`, `CONTACT_PHONE` (пункт «Позвонить» в виджете; пусто → пункта нет), `CHAT_HOURS` / `CHAT_TZ` (часы работы чата; по умолчанию 09:00-21:00 и Europe/Moscow), `TG_BOT_URL` (ссылка в шапке и пункт виджета связи; пусто → нет ни того, ни другого), `MAX_URL` (пункт MAX в виджете связи; пусто → пункта нет), `SITE_URL` (база canonical/OG/sitemap; пусто → абсолютные SEO-ссылки отключены), `USE_FORWARDED_HEADERS`, `MEDIA_ENDPOINT` (адрес S3; пусто → фото берутся из wwwroot), `MEDIA_BUCKET`, `MEDIA_PUBLIC_PATH` (путь, по которому nginx отдаёт бакет), `MEDIA_ACCESS_KEY` / `MEDIA_SECRET_KEY` (учётка только на чтение), `MEDIA_REFRESH_MINUTES` |
| gateway | `JWT_ISSUER`, `JWT_KEY`, `UI_APP_URL` (белый список CORS), `USE_FORWARDED_HEADERS` |
| users | `DB_READ_CONNECTION_STRING`, `DB_WRITE_CONNECTION_STRING`, `HTTP_PORT` |
| chat | `DB_READ_CONNECTION_STRING`, `DB_WRITE_CONNECTION_STRING` (схема `chat`), `HTTP_PORT`, `TG_BOT_TOKEN` (пусто → бот выключен), `TG_ADMIN_CHAT_ID` (группа гидов; пусто → сообщения сохраняются, но не уходят), `TG_ADMIN_LANG` (язык служебных сообщений в группе, по умолчанию `ru`), `CHAT_RETENTION_DAYS` (срок хранения переписки, по умолчанию 90; `0` и меньше выключают чистку), `SITE_URL` (куда ведёт кнопка бота) |
